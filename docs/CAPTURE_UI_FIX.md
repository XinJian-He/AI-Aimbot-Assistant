# ImGui 采集设备修复（2026-09-30）

修改项目：`E:\AIaim\aim-QQLive-DML1`。
参考：`E:\AIaim\AI\AiMod\cap` 的 CardCapture、FrameGrabber、MF / DirectShow 采集链路与 JpegCodec。

## 修改与依据

- 原来的设备列表只在 MF 结果为空时使用 DirectShow。现在合并两个列表，按设备路径去重，不按名称去重；没有 DevicePath 时使用 moniker display name。MF / DirectShow 枚举错误会返回 UI。
- 设备列表和格式列表分开异步读取，进入采集卡页自动枚举；先显示设备，再读取所选设备格式。删除两项重复的原始文本输入，仅保留设备、格式下拉框及刷新。设备改变会清除旧格式，迟到的结果按请求代次丢弃。
- UI 原来会在渲染线程同步读配置，等待模型加载持有的锁。现在状态、日志、配置和文件列表由后台快照任务读取，配置锁繁忙时跳过配置刷新，日志页在启动期间仍可查看。操作前后用版本号丢弃旧参数快照，避免覆盖刚提交的值。
- 新增 `Aim_IsProcessingIdle`，只有采集、推理都停止且控制操作结束才允许读取格式、确认暂停。停车等待设置 5 秒上限，超时后中止本次操作，不销毁仍在使用的推理对象。参数写入锁繁忙时快速返回。
- 新增成功发布帧计数 `Aim_GetCaptureFrameCount`。开始操作只有收到新画面才报告成功，15 秒内未完成则显示具体状态；开流后连续 5 秒无画面写入日志。
- MF 初始化改为 FULL，并检查错误。MJPEG 允许 MF 解码器；DirectShow 的压缩帧经现有 WIC JPEG 解码器转换为 BGR24 后交给原采集链路。MF 开流失败后先释放源、reader 和 activation，再尝试 DirectShow。

保留指定设备、分辨率和帧率约束，不因所选设备失败而自动打开另一台摄像头。图像仍通过原采集、推理和实时预览窗口输出。

## 手动验证

本次没有编译或启动程序，也没有连接、关闭或抢占采集硬件。静态检查不能证明设备实机成功。

1. 关闭旧版程序，VS 选择 `Release | x64`，重新生成整个解决方案（包括 aimlib 和 host_test），使用同次生成的 EXE / DLL。
2. 启动后进入设备页的图像采集，选择采集卡。检查列表出现内置摄像头及外接采集卡，名称正确且没有两项多余文本输入。
3. 选择目标设备，等格式列表返回，先选择设备确实支持的 NV12 / YUY2 格式。选择可用 ONNX 模型，开启“实时预览”，点击开始。
4. 成功标准：提示“已收到采集画面”，原预览窗口持续更新，FPS 随画面更新。加载期间切换到日志页、拖动窗口仍应响应。
5. 暂停后刷新格式，再次开始，应恢复画面；换设备时旧格式不应残留。另测设备支持的 MJPG 模式。
6. 断开输入信号、被其他程序占用、选择无法打开的设备时，应显示具体失败或无画面信息，不得报告启动成功或自动换成摄像头。
7. 设备枚举失败后重新插接并“刷新设备”；没有任何设备时应显示空列表说明。加载另一个配置后检查设备、格式与配置一致。

## 限制

驱动的同步 COM 调用、模型加载本身不能在进程内安全强制终止。8 秒枚举提示与 15 秒启动提示是状态反馈，不代表底层操作已取消。若驱动永久不返回，界面消息循环仍可运行，但依赖该设备的操作及安全退出仍可能等待；没有使用强杀线程或分离后继续访问已销毁对象。

日志位于 `%TEMP%\aim_pushlog.txt`，旧日志混有多次进程记录，无法作为本次实机通过的证据。若复现失败，请保留本次开始至失败期间的 UI 日志、所选设备/格式及预览现象。
